# SQLite Registration Authentication Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the fixed demo credentials with persistent SQLite accounts, a registration route, hashed passwords, and JWT login while keeping `/api/me` and Swagger usable.

**Architecture:** Express app setup moves to `src/app.js`; `src/server.js` loads configuration and starts listening. Separate auth and profile routers use a database module and a Bearer verification middleware. SQLite stores users at `data/auth.sqlite`; bcryptjs stores only password hashes.

**Tech Stack:** Node.js 20+, Express 5, better-sqlite3, bcryptjs, jsonwebtoken, Swagger UI.

**Spec:** `docs/superpowers/specs/2026-10-18-sqlite-registration-auth-design.md`

## Global Constraints

- Store the SQLite database at `data/auth.sqlite` and keep it out of Git.
- Use a case-insensitive unique username, trimmed and validated against `^[A-Za-z0-9_.-]{3,32}$`.
- Require passwords of at least 8 characters and at most 72 UTF-8 bytes.
- Hash passwords asynchronously with bcryptjs at 12 rounds; never return hashes.
- Keep the database empty on first startup; do not seed `admin/password`.
- Issue HS256 JWTs with the SQLite user id in `sub`, the username claim, and a one-hour expiration.
- Preserve the current `GET /api/me` response and use `JWT_SECRET` from the environment.
- Keep Swagger at `/api-docs`, including in production.

## Review Focus

- Registration usernames differing only by case must conflict with `409 username_taken`.
- Username trimming and allowed-character/length validation must produce a consistent stored username or `400 invalid_request`.
- A password over 72 UTF-8 bytes must be rejected before bcrypt hashes it.
- Missing accounts and wrong passwords must produce the same `401 invalid_credentials` response.
- Missing, malformed, expired, or incorrectly signed Bearer tokens must still produce `401 unauthorized`.

### Task 2: Separate Express setup and implement database-backed routes

**Files:**
- Create: `src/app.js`
- Modify: `src/server.js`
- Create: `src/routes/auth.routes.js`
- Create: `src/routes/me.routes.js`
- Create: `src/middleware/require-auth.js`

**Interfaces:**
- Consumes: `findUserByUsername` and `createUser` from Task 1.
- Produces: an Express app exported by `src/app.js`; `src/server.js` loads dotenv, requires `JWT_SECRET`, and starts the app on `PORT` or `3000`.
- The auth router mounted under `/api` owns `/register` and `/login`; the profile router mounted under `/api` owns `/me`.
- `require-auth.js` verifies the Bearer token with only HS256 allowed and attaches the verified `{ id, username }` identity to the request.

- [ ] Move Express app creation, JSON parsing, Swagger mounting, route mounting, and JSON error middleware into `src/app.js`.
- [ ] Keep `src/server.js` as the dotenv/configuration and listen entry point; preserve `PORT` and the mandatory `JWT_SECRET` behavior.
- [ ] Implement registration validation: trim username; enforce 3–32 allowed ASCII characters; require a string password of at least 8 characters and at most 72 UTF-8 bytes; return `400 { "error": "invalid_request" }` for invalid input.
- [ ] Hash valid registration passwords with asynchronous `bcryptjs.hash(password, 12)`, insert through `createUser`, and return `201` with `{ user: { username }, token, token_type: "Bearer", expires_in: 3600 }`.
- [ ] Map SQLite username uniqueness violations to `409 { "error": "username_taken" }`; do not return SQL details.
- [ ] Implement login using `findUserByUsername` and asynchronous `bcryptjs.compare`; return the existing token response on success and the same `401 { "error": "invalid_credentials" }` for unknown usernames and wrong passwords.
- [ ] Reject missing/non-string login fields or passwords over 72 UTF-8 bytes with `400 { "error": "invalid_request" }` before querying SQLite.
- [ ] Sign tokens with the user id encoded as a string in `sub`, username as a claim, HS256, and a one-hour expiration.
- [ ] Move token extraction and verification into `require-auth.js`; require a string `sub` and username claim, attach them as the verified identity, preserve `GET /api/me` success shape `{ "user": { "username": "..." } }`, and return `401 { "error": "unauthorized" }` for token errors.
- [ ] Map only SQLite's unique-constraint error for the username field to `409`; return generic JSON `500` for other database errors.
- [ ] Remove the hard-coded `ADMIN_USERNAME` and `ADMIN_PASSWORD` login path; keep startup and route modules free of seeded accounts.
